Para seu SPI VIP, eu adotaria inicialmente:
- spi_driver como mestre ativo.
- clk e rst_n controlados externamente.
- Uma única task de transmissão serial de 40 bits.
- Tasks específicas para READ e WRITE.
- spi_miso ignorado quando não houver retorno válido.
- Período de SPI configurável.
- Tratamento de reset durante uma transferência.
- Monitor independente do driver, reconstruindo os frames diretamente dos sinais.
A decisão arquitetural mais importante é esta: uma operação de leitura deve ser representada por um único spi_item de alto nível, mesmo que o driver execute dois frames SPI físicos.

Assim, a sequence solicita simplesmente uma leitura de REG_KEY0, e o driver se responsabiliza pelo READ request e pelo NOP de retorno.

Isso mantém as sequences simples e deixa toda a implementação do protocolo concentrada no driver.

Monitor 

onforme o Block Guide, o SPI opera em Mode 0:
- spi_sclk fica em 0 quando o barramento está ocioso.
- MOSI é amostrado na borda de subida.
- MISO é atualizado pelo DUT na borda de descida.
- O frame possui 40 bits e é transmitido MSB-first.

Monitor por frame: publica um item para cada frame de 40 bits. Nesse caso, a associação entre READ REQUEST e NOP pode ficar no scoreboard ou em outro componente.

Monitor por operação: reconstrói a operação completa e publica um único item de leitura, mesmo que ela utilize dois frames.

Para o seu SPI VIP, eu escolheria inicialmente o monitor por operação, mantendo internamente a capacidade de identificar cada frame. Isso combina com a proposta de usar um único spi_item para cada leitura ou escrita.
